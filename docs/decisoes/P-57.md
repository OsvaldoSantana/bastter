# P-57 — onde a captura roda: GitHub Actions + Cloudflare R2

**Decidida em 24/09/2026.** Decisão técnica delegada ao Claude pelo Osvaldo, com o executor
e o armazém escolhidos por ele. Este documento é o desenho, as alternativas descartadas, os
riscos e as defesas. A implementação está no mesmo commit.

## O problema, em uma linha

A CVM reescreve DFP e ITR toda semana e não guarda a versão anterior (CV-01). Cada semana
sem captura é uma rodada de reapresentações que **não volta**. A captura existia como
comando (`fase0/capturar_cvm.py`) e dependia de a máquina dele estar ligada e de alguém
lembrar. A P7 admite duas saídas e só duas: rodar sem humano, ou ser declarada como
limitação. Esta é a primeira.

## O desenho

```
cron diário (09:15 UTC)                                   git (público)
        │                                                 docs/acervo/cvm/capturas.csv
        ▼                                                 docs/acervo/<fonte>/inventario-armazem.csv
GitHub Actions ── HEAD em cada arquivo do índice ──┐            ▲
  (runner efêmero)                                 │            │ só quando muda
        │  mudou? GET → temporário → Content-Length │            │
        │         + testzip (regra 2.5)             │            │
        ▼                                           ▼            │
Cloudflare R2  cvm/<recurso>/<arquivo>/<sha256>.<ext>  ◄── sobe se ausente
               logs/capturas/<AAAA-MM-DD>.csv          ◄── a rodada inteira, sempre
```

| peça | arquivo | o que faz |
|---|---|---|
| executor | `.github/workflows/captura_cvm.yml` | cron diário + manual; sem sobreposição; commita o registro se mudou; falha = job vermelho (e-mail do GitHub) |
| captura | `fase0/capturar_cvm.py --armazem s3` | o mesmo portão HEAD e a mesma conferência do modo disco; sobe pela chave de conteúdo |
| armazém | `fase0/armazem.py` | `existe`, `enviar_se_ausente`, `baixar`, `listar`. Nunca sobrescreve. Confere o sha256 na subida e na descida |
| leitura | `fase0/acervo.py` | `abrir(recurso, arquivo, versao)` devolve caminho local conferido; `frescor(recurso)` avisa com mais de 8 dias sem observação |
| carga inicial | `fase0/subir_acervo_local.py` | sobe uma vez o que só existe no disco dele (CVM com snapshots, COTAHIST). Plano por padrão, `--aplicar` para executar |

**A chave é o conteúdo.** `<fonte>/<recurso>/<arquivo>/<sha256>.<ext>`: duas versões são duas
chaves, a mesma versão é sempre a mesma chave. Por isso "nunca sobrescrever" não é disciplina,
é consequência — e o `_snapshots/` do disco não tem par no armazém: toda versão já tem
endereço.

**O git guarda o que existe; o armazém guarda o byte.** A lista de versões sai do registro e
do inventário, versionados. A chave se deriva de (fonte, recurso, arquivo, sha256). Se o
armazém sumisse, a lista ficaria de pé e cada `abrir` diria qual byte falta.

**O registro se parte em dois**, e a divisão foi pedida por ele:

| linha | vai para | por quê |
|---|---|---|
| `novo`, `atualizado`, `rejeitado`, `erro` | `capturas.csv` (git) | muda o estado, ou é falha |
| `inalterado` pelo portão HEAD | log do armazém | com captura diária seriam 365 commits de ruído por ano; a prova de execução continua existindo |
| `inalterado` por **hash coincide** | `capturas.csv` (git) | **desvio do pedido, e o motivo é medido:** a CVM regera o arquivo com `Last-Modified` novo e o mesmo byte. Essa linha é a única que carrega o `Last-Modified` novo para o estado; sem ela o portão compara sempre com o velho e **baixa o mesmo arquivo todo dia, para sempre**. `test_hash_coincide_vai_ao_registro_e_fecha_o_portao_na_rodada_seguinte` reprova se ela for só para o log |

Os dois modos (disco e armazém) escrevem o mesmo `caminho` lógico no registro e **compartilham
o portão**: uma captura na máquina dele e depois uma na nuvem não baixam duas vezes.

## As alternativas descartadas

| alternativa | por que não |
|---|---|
| **Agendador de Tarefas do Windows** | depende do PC ligado, e a máquina dele fica desligada quase sempre. É o lembrete da W-01 com outro nome |
| **Anexos / releases / LFS de repositório privado do GitHub** | o GitHub não é armazenamento — é onde o código e o registro moram. Release e LFS servem para distribuir software (cotas e políticas não lidas aqui), e o repositório é **público** (P-62): o byte da fonte iria junto |
| **commitar os ZIPs no próprio repositório** | a P-98 e o `test_p98_acervo_fora_do_indice.py` existem para impedir exatamente isto |
| **Supabase como executor** | o projeto Free pausa após 1 semana de inatividade (`docs/fontes/executor-da-rotina-semanal.md`) — uma rotina semanal viveria em cima do limiar |
| **guardar só o delta no git** (§11.6, 06/09) | a comparação por conteúdo que o delta exige é o `manifesto_cvm.comparar()`, e ela não roda no runner sem os dois ZIPs inteiros. Guardar a versão inteira no R2 é mais simples e não perde nada. A carga inicial ocupa 1,5 GB dos 10 GB grátis (§11.6); o ritmo de crescimento **não foi medido** — `NAO_CONFIRMADO` até haver algumas semanas de log |

## Os riscos, e a defesa de cada um

| risco | defesa |
|---|---|
| **o GitHub desliga o cron** depois de 60 dias sem atividade no repositório — sem erro, a série só para de crescer | `acervo.frescor()`: mais de 8 dias sem observação → `CapturaParada`, nomeado, e `abrir()` o mede toda vez que alguém pede um arquivo da CVM. `python fase0/acervo.py --frescor` sai 1 quando algum recurso está parado. E o próprio commit semanal do registro (a CVM muda toda semana) é atividade |
| download cortado ou ZIP corrompido aceito como versão | a regra 2.5 vale igual no modo armazém: `Content-Length` e `testzip` **antes** de subir. Falhou → `rejeitado`, nada sobe, job vermelho |
| chave que mente sobre o conteúdo | `enviar_se_ausente` recalcula o sha256 do arquivo e recusa se não bater com a chave; `baixar` confere o que voltou antes de aceitar |
| índice vazio lido como "nada a capturar" | continua sendo erro (`alvos()` levanta), vira linha `erro` no registro e no log, job vermelho |
| duas capturas simultâneas | `concurrency` no workflow, sem cancelar a que roda. A corrida residual entre `existe` e `enviar` escreveria o mesmo byte duas vezes — inofensiva, porque a chave é o conteúdo |
| credencial vazando no log público | só por variável de ambiente, vinda de segredo; nenhum passo imprime; a mensagem de falta diz o **nome** da variável; `repr` do armazém mostra só o bucket. Testado |
| o registro não sobe porque a captura falhou | o passo de commit é `if: always()` e vem **antes** do passo que deixa o job vermelho |
| push rejeitado por commit concorrente dele | `git pull --rebase` antes do push; conflito no `capturas.csv` deixa o job vermelho — visível, nunca silencioso |
| o log do armazém como única prova de uma rodada sem mudança | aceito: o `frescor` sem credencial mede só o registro, e diz isso (`consultado: ["registro"]`) em vez de fingir que olhou o log |

## Uma correção ao pedido, medida

O pedido desta decisão mandava declarar, como `NAO_CONSERTADA`: *"o COTAHIST não é capturado
na nuvem porque a página da B3 exige validação por imagem, que não se contorna."* **Isso é a
afirmação que a §5-B.13 retratou em 18/09**, e foi medido de novo hoje:

```
HEAD https://bvmf.bmfbovespa.com.br/InstDados/SerHist/COTAHIST_A2026.ZIP
HTTP/1.1 200 OK · Content-Length: 84469516 · Last-Modified: Wed, 23 Sep 2026 23:43:07 GMT
ETag: "d0e7bd48b54bdd1:0" · Server: cloudflare
GET Range 0-3 de COTAHIST_A2025.ZIP → 50 4b 03 04 (PK)
```

A validação por imagem está no **formulário** de séries anuais; o arquivo está num GET aberto,
com `Last-Modified` e `ETag` — a mesma forma da CVM, portão HEAD incluído. O que **não** se
sabe é se a B3 (atrás da Cloudflare) responde igual a um IP de datacenter do GitHub. Por isso a
limitação entrou como *"ainda não é capturado na nuvem"*, com `o_que_resolveria` = estender a
captura e medir a resposta ao runner, e não como impossibilidade.
